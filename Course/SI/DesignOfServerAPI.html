API - 系統間的溝通橋樑

  • 定義： API (Application Programming Interface) 是一組定義了軟體組件如何互相通訊的規則。
  • 重要性：
    • 互通性： 實現前後端分離、不同服務間的協作。
    • 效率： 加速開發，實現功能複用。
    • 擴展性： 便於功能迭代與系統擴展。
  • 為何需要設計規格？
    • 一致性： 統一開發標準，減少溝通成本。
    • 穩定性： 減少錯誤，提高系統可靠性。
    • 易用性： 讓其他開發者能快速理解和使用。
    • 可維護性： 方便長期迭代與更新。

RESTful API - 現代 Web API 設計典範

  • REST 簡介： Representational State Transfer (表述性狀態轉移)
  • 核心理念： 將一切視為資源 (Resource)，透過標準的 HTTP 方法對資源進行操作。
  • 關鍵原則 (簡化)：
    • 客戶端-伺服器分離 (Client-Server Separation)
    • 無狀態 (Stateless)：每個請求獨立，伺服器不保存客戶端狀態。
    • 可快取 (Cacheable)
    • 統一介面 (Uniform Interface)：使用標準方法和資源命名。

資源導向的 URI 設計

  • 什麼是資源 (Resource)？
    • API 中的核心概念，可以是物件、數據集合、服務等 (e.g., 使用者 users, 訂單 orders, 產品 products)。
  • URI (Uniform Resource Identifier)： 資源的唯一標識符。
  • 設計原則：
    • 名詞化： 使用名詞表示資源，避免使用動詞。
    • 複數形式： 集合資源使用複數名詞 (e.g., /users, /products)。
    • 巢狀關係： 透過 / 表示資源間的層次關係 (e.g., /users/{id}/orders)。
    • 簡潔、可讀性高。
  • 範例：
    • 獲取所有用戶：GET /users
    • 獲取特定用戶：GET /users/{id}
    • 獲取特定用戶的所有訂單：GET /users/{id}/orders

利用 HTTP 方法表達操作意圖

  • CRUD
    • 全稱： Create（新增）、Read（讀取）、Update（更新）、Delete（刪除）。
    • 含義： 這是資料庫操作的四個基本功能，也是大多數應用程式與資料互動的核心模式。
    • 例子： 在部落格系統中，寫新文章是 Create，閱讀文章是 Read，編輯文章是 Update，刪除文章是 Delete。
  • HTTP 方法與 CRUD 操作的對應：
    • GET (Retrieve/讀取)： 獲取資源。
    • POST (Create/創建)： 創建新資源。
    • PUT (Update/替換)： 完全替換資源。
    • PATCH (Update/部分更新)： 部分更新資源。
    • DELETE (Delete/刪除)： 刪除資源。
  • 冪等性 (Idempotency) 與安全性 (Safety)：
    • 安全方法： GET (不改變伺服器狀態)。
    • 冪等方法： GET, PUT, DELETE (重複執行結果一致)。
  • 避免濫用： 不應所有操作都使用 POST。

透過狀態碼明確溝通請求結果

  • 1xx (資訊性)： 請求已接收，繼續處理。
  • 2xx (成功)：
    • 200 OK：請求成功，回應體包含數據。
    • 201 Created：新資源已成功創建 (POST, PUT)。
    • 204 No Content：請求成功，但回應體無內容 (PUT, DELETE)。
  • 3xx (重定向)： 資源需要進一步操作才能完成。
  • 4xx (客戶端錯誤)：
    • 400 Bad Request：請求格式錯誤或參數無效。
    • 401 Unauthorized：未經認證 (需要登入)。
    • 403 Forbidden：無權限 (已認證但無權訪問)。
    • 404 Not Found：資源不存在。
    • 429 Too Many Requests：請求過於頻繁 (速率限制)。
  • 5xx (伺服器錯誤)：
    • 500 Internal Server Error：伺服器內部錯誤。
    • 503 Service Unavailable：伺服器暫時無法處理請求。

數據交換的語言 - JSON 與 MIME Type

  • JSON (JavaScript Object Notation)：
    • 輕量級、易讀寫的數據交換格式。
    • 結構： 物件 {} 和陣列 []。
    • MIME Type： application/json。
    • 應用： 現代 API 數據交換的主流格式。
  • MIME Type (用於表單數據)：
    • application/x-www-form-urlencoded： 表單預設，key=value&key=value 格式，不支持文件。
    • multipart/form-data： 專用於文件上傳，將數據分割為多個部分。
  • Content-Type Header： 在請求和回應中指定 Body 的格式。

管理 API 演進 - 版本控制

  • 為何需要？ 確保向後兼容，允許 API 迭代和功能擴展。
  • 常見策略：
    • URI 版本化 (URL Versioning)：
      • 範例：/v1/users, /v2/users
      • 優點： 直觀、易於理解和快取。
      • 缺點： 改變 URI 會影響路由和鏈接。
    • Header 版本化 (Header Versioning)：
      • 範例：Accept: application/vnd.example.v1+json
      • 優點： URI 更簡潔，客戶端彈性大。
      • 缺點： 不直觀，不易快取，可能需要自定義 Header。
    • Query Parameter 版本化 (較不推薦用於 RESTful)：
      • 範例：/users?version=1

保護您的 API - 認證與授權

  • 認證 (Authentication) - 你是誰？ 證明用戶身份。
    • API Keys： 簡單，透過 Header 傳遞。
    • OAuth 2.0： 行業標準，用於授權第三方應用程式訪問資源。
      • OAuth (Open Authorization)
      • 含義： 開放授權 標準，它允許使用者授權第三方應用程式存取其在另一個服務（如 Google、Facebook）上的有限資源，而無需向第三方應用程式提供其帳號密碼。
      • 目的： 主要用於授權委託，解決「讓 A 網站安全地存取我 B 網站的某些資料」的問題。
      • 例子： 當您使用「Google 登入」某個 App 時，OAuth 負責處理這個授權流程。
    • JWT (JSON Web Tokens)： 輕量級安全認證，可用於無狀態的認證。
      • JWT (JSON Web Token)
      • 含義： JSON 網頁權杖，是一種用於在網路應用程式之間安全傳輸資訊的開放標準。它是一個緊湊且自包含的格式。
      • 組成： 通常包含三部分：Header（頭部）、Payload（負載，存放實際資訊如使用者 ID、權限等）、Signature（簽名）。
      • 目的： 主要用於身份驗證和資訊傳輸。服務端可以透過驗證簽名來確認權杖的真偽和資訊是否被竄改。它常與 OAuth 搭配使用，作為 OAuth 授權流程中發放的存取權杖（Access Token）的實現方式。
      • 特點： 無狀態 (Stateless)，伺服器不需要儲存工作階段 (Session) 資訊，只檢查 JWT 即可。
  • 授權 (Authorization) - 你能做什麼？ 判斷用戶是否有權限執行操作。
    • 基於角色的訪問控制 (RBAC)。
  • 實作考量： 如何在每次 API 請求中驗證身份和權限。

友善的錯誤訊息與統一的錯誤格式

  • 統一錯誤格式：
    • 返回 JSON 格式的錯誤訊息。
    • 包含 code (錯誤代碼)、message (人類可讀的錯誤訊息)、details (更多詳細資訊，如哪個字段錯誤)。
  • 結合 HTTP 狀態碼： 錯誤類型應與 HTTP 狀態碼對應。
    • 400 Bad Request + 錯誤詳細訊息 (e.g., 密碼格式不正確)。
    • 404 Not Found + 資源不存在的訊息。
    • 500 Internal Server Error + 建議稍後重試的訊息。
  • 避免洩露敏感資訊： 錯誤訊息不應暴露內部實現細節。

讓您的 API 易於理解和使用

  • 文件的重要性： 它是 API 的「說明書」，減少溝通成本，加速接入。
  • OpenAPI Specification (OAS / Swagger)：
    • 標準化的 API 描述語言，可以生成互動式文件。
    • 含義： 一套用於設計、建構、文件化和消費 RESTful Web 服務的工具集和規範。
    • 目的： 讓前後端開發人員、測試人員和文件撰寫人員能夠輕鬆地理解和使用 API。
    • 主要功能：
      • 文件自動生成： 根據程式碼或定義檔案，自動產生美觀且互動式的 API 文件。
      • API 試用介面： 通常提供一個網頁介面 (Swagger UI)，可以直接在瀏覽器中測試 API。
      • 標準化： 幫助團隊以標準化的方式定義 API 規格。
    • 工具：Swagger UI, Postman, Redoc 等。
  • 文件內容應包含：
    • 基本資訊 (標題、版本、描述)。
    • 所有端點 (URI, 方法)。
    • 參數 (類型、是否必填、說明)。
    • 回應格式 (成功與錯誤)。
    • 認證方式。
    • 範例請求和回應。

API 規格設計的黃金法則

  • 一致性： 命名、格式、錯誤處理保持一致。
  • 可讀性： URI 簡潔，JSON 結構清晰。
  • 簡潔性： 不返回過多客戶端不需要的數據。
  • 可預測性： 客戶端應能根據規格預測 API 行為。
  • 安全性： 始終考慮認證、授權和輸入驗證。
  • 演進性： 規劃版本控制，考慮未來的擴展。
  • 文件化： 確保 API 文件清晰、最新。
