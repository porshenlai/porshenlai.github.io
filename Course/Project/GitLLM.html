💡 模組化設計簡介 (Modular Design) [1/3]

🎯 什麼是模組化設計？

  • 定義： 將一個複雜的系統分解成數個獨立、可替換、標準化的組件（即模組），每個模組負責系統中的特定功能。
  • 目標： 提高系統的靈活性、可維護性、可重用性和效率。

🌟 1) 核心好處 (Key Benefits)

類別 好處說明 效益
🛠️ 管理與維護 (Management & Maintenance) 獨立的模組更容易單獨測試、除錯和更新。 降低整體系統的複雜度和維護成本。
🛡️ 安全與風險控制 (Security & Risk Control) 故障或安全漏洞可隔離在單一模組，不會影響整個系統。 限制錯誤的擴散範圍，提升系統的穩定性和彈性。
🚀 效率與重用性 (Efficiency & Reusability) 設計好的模組可重複使用於多個專案或系統的不同部分。 縮短開發時間，提高資源利用率，降低重複開發成本。
🔄 擴展與彈性 (Scalability & Flexibility) 系統功能可透過增加或替換模組來實現快速擴展和調整。 滿足未來業務成長和需求變化。

📝 2) 重點工作 (Key Tasks)

  • 系統分析與功能劃分 (System Analysis & Functional Decomposition):
    • 識別並定義系統的主要功能。
    • 將功能拆解為獨立的模組邊界。
  • 資源規劃與標準化 (Resource Planning & Standardization):
    • 規劃模組所需的資源（人力、技術、時間）。
    • 制定模組間一致的介面和標準。
  • 協定與介面設計 (Protocol & Interface Design):
    • 定義模組間溝通的方式和資料格式（API, 協定）。
    • 確保模組具備高內聚力（Cohesion）和低耦合度（Coupling）。
  • 說明文件與知識庫建立 (Documentation & Knowledge Base):
    • 為每個模組撰寫清晰的規格書和使用手冊。
    • 建立中央知識庫以便團隊成員理解和重用。

Prompt 即 Commit Log 的重要性

  • 可追溯性 (Traceability): 每次 Commit 的程式碼修改，都必須對應到產生它的 Prompt。
  • 協作基礎: 隊友檢視程式碼時，可以立即從 Log 了解「最初的設計意圖」。
  • 未來優化: 累積的 Prompt 歷史是未來訓練或微調 LLM 的寶貴資料集。

Commit Log 格式建議

欄位內容目的
標題 (Subject)[Prompt]: <核心提示詞>快速了解本次修改的驅動指令。
內文 (Body)*可選*，詳細說明本次人工微調/測試結果。提供額外的脈絡與驗證細節。

💡 範例：[Prompt]: 請寫一個計算斐波那契數列的 Python 函式，並加上型別註記。

實戰演練：步驟一：初版程式碼生成與上傳

  1. 設計 Prompt: 撰寫第一個清晰、明確的提示詞 (例如：[Prompt]: 請用 C++ 寫一個計算質數的函式，並包含測試用例。)。
  2. LLM 生成: 將 Prompt 輸入給 LLM，取得程式碼。
  3. Git 提交: 將程式碼檔案加入 Git，並使用完整的 Prompt 作為 Commit Log 提交。 
    git add <檔案名>
git commit -m "[Prompt]: 請用 C++ 寫一個計算質數的函式，並包含測試用例。"
  4. 推送到 GitHub:
    git push origin <branch>。

實戰演練：步驟二：團隊 Code Review 與缺陷標記

  • GitHub Pull Request (PR): 提交 PR 進行審核。
  • Code Review: 隊友閱讀程式碼，並在 PR 介面中留下具體修改建議。
  • 使用 git blame： 在 GitHub 介面上，點擊 blame 鍵，每一行程式碼都會指向第一個 Prompt Commit，證明其來源。

何謂 Pull Request (PR) [1/2]

在 GitHub 中，Pull Request (PR)，通常譯為「提取請求」或「拉取請求」，是協同合作的核心機制之一。

什麼是 Pull Request (PR)？

Pull Request 是一種提案，目的是將一個分支（通常是包含你的修改的分支，稱為「來源分支」或 head branch）的變更合併到另一個分支（通常是專案的主要分支，如 main 或 master，稱為「目標分支」或 base branch）。

簡單來說，它就是請求專案的維護者「拉取」你的程式碼變更到他們的主程式碼庫中。

PR 的主要作用：

  1. 代碼審查 (Code Review)：PR 提供了一個集中的平台，讓團隊成員或專案維護者可以查看、討論、評論和審核你所提出的所有變更內容（文件的差異比較/diffs）。

  2. 協作與討論：在正式合併之前，團隊可以針對變更提出建議、要求修改，或確保代碼品質、一致性和專案標準。

  3. 安全性：確保變更在經過充分審查和測試之後，才能被合併到主分支，避免未完成或有問題的代碼破壞專案的穩定性。

何謂 Pull Request (PR) [2/2]

如何進行 Pull Request？

無論你是貢獻給自己的專案還是其他人的開源專案，Pull Request 的基本流程通常包含以下步驟：

1. 準備變更 (在本地)

  • 建立新分支 (Branch)：始終在一個新的、具有描述性的分支上進行工作（例如：feature/add-login 或 fix/bug-on-homepage），而不是直接在 main 或 master 分支上。

    Bash 
    git checkout -b your-new-branch-name

  • 進行修改：在你的新分支上進行代碼編寫、新增功能或修復錯誤。

  • 提交變更 (Commit)：將你的變更提交到本地 Git 歷史中。

    Bash 
    git commit -m "Descriptive commit message"

2. 推送變更到遠端倉庫 (Push)

  • 推送到 GitHub：將你本地的新分支推送到你的 GitHub 遠端倉庫。

    Bash 
    git push origin your-new-branch-name

    如果你是貢獻給別人的專案，通常你需要先 Fork (複製) 該專案到你的 GitHub 帳號下，然後將你的變更推送到你的 Forked 倉庫。

3. 建立 Pull Request (在 GitHub 網站)

  • 發起 PR：

    • 方法一 (GitHub 介面提示)：推送完成後，GitHub 網頁通常會在你的倉庫頁面出現一個黃色的橫幅或提示，讓你「Compare & pull request」（比較並發起提取請求），點擊它。

    • 方法二 (手動)：導航到 GitHub 倉庫的 Pull requests 頁籤，點擊綠色的 New pull request 按鈕。

  • 選擇分支：

    • Base branch (目標分支)：選擇你希望變更合併到的目標分支（例如 main 或 master）。

    • Compare branch (來源分支)：選擇你剛才推送變更的新分支。

  • 填寫標題和描述：

    • 標題 (Title)：簡潔明瞭地說明你的 PR 目的。

    • 描述 (Description)：詳細說明你做了哪些變更、為什麼要做這些變更，以及它解決了什麼問題（可以連結相關的 Issue）。

  • 送出 PR：點擊 Create pull request (或 Create draft pull request 如果你還沒準備好審核)。

4. 審查與討論 (Review & Discussion)

  • PR 建立後，專案維護者或協作者會被通知進行審查。

  • 他們會在你的 PR 頁面上留下評論，可能會要求你進行額外的修改。

  • 如果你需要修改：回到本地分支進行修改、Commit，然後再次 Push 到你的遠端分支。所有新的 Commits 都會自動新增到你現有的 PR 中。

5. 合併 (Merge)

  • 一旦所有審查意見都已解決，並且代碼通過了必要的測試（例如 CI/CD 檢查），專案維護者就會點擊 Merge pull request 按鈕，將你的變更合併到目標分支。

  • 合併完成後，該 PR 就會被關閉 (Closed)，你的變更正式成為專案的一部分。

實戰演練：步驟三：設計新的 Prompt 進行修正

  • 意見收斂: 根據 Code Review 的建議，設計出一個新的、更精確的 Prompt。
  • 新 Prompt 範例: 
    [Prompt]: 請修正函式中對偶數的錯誤判斷，並將 C++ 的測試用例改用 Catch2 框架實現。
  • LLM 修正: 將舊程式碼 + 新 Prompt 傳給 LLM，要求其修正。

實戰演練：步驟四：檢視差異與版本更新

  1. 檢視差異 (Diff): 在本地使用 git diff 仔細比較 LLM 做了哪些修改。
  2. 提交修正: 使用新的 Prompt 作為 Commit Log 提交。 
    git add <檔案名>
    git commit -m "[Prompt]: 請修正函式中對偶數的錯誤判斷，並將 C++ 的測試用例改用 Catch2 框架實現。"
  3. 推送到 GitHub: 進行第二次 push。
思考： 如果 LLM 的修正不完整或引入新錯誤，你該怎麼辦？ (答：設計第三版 Prompt)

總結：Log, Diff, Blame 的威力

Git 核心功能如何服務於 LLM 開發

  • git log 追蹤歷史: 執行 git log --oneline，你看到的是完整的 Prompt 演化歷史，而非單純的程式碼修改。
  • git diff 驗證修正: 確保 LLM 的修改範圍和內容是可控且符合預期的，避免「黑箱」修正。
  • git blame 溯源責任: 任何一行程式碼，都能追溯到是哪一個 Prompt 驅動了它的生成，提升問題排除效率。
