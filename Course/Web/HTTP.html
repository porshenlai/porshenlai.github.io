總體結構概覽

無論是 HTTP 請求還是回應，其基本結構如下：

[起始行 (Start Line)] 包含方法/狀態碼、URI/狀態文本、HTTP版本
[標頭 (Header)] 包含多個鍵值對，提供額外資訊
[空行] 標頭和實體之間的分隔符
[實體 (Body)] 包含實際傳輸的數據 (可選)

Header (標頭)

Header 是由一系列的鍵值對 (Key-Value Pairs) 組成，每個鍵值對佔一行，格式為 Key: Value。所有標頭結束後，會有一個空行來表示標頭的結束，並與 Body 分隔。

定義格式：

  • 每個標頭都是一行文字。
  • 格式為 Header-Name: Header-Value。
  • Header-Name 不區分大小寫，但慣例是使用大寫字母開頭並用連字號 - 分隔單詞 (例如 Content-Type)。
  • Header-Value 可以是任何字串，其具體含義由 Header-Name 定義。
  • 標頭之間沒有固定的順序要求，但通常會有慣例。
  • 最後一個標頭之後必須跟一個空行 (只有 CR 和 LF 字符)，表示標頭部分的結束。

功能：

Header 的主要功能是提供關於訊息本身、發送方、接收方、請求/回應的元數據 (Metadata)，而不是實際要傳輸的應用層數據。它協助客戶端和伺服器正確地解析、處理和傳輸 Body 中的數據。

常見的 Header 類別和功能：

  1. 通用標頭 (General Headers)：
    • 適用於請求和回應。
    • Date: 訊息發送的日期和時間。
    • Connection: 控制網路連線是持久的 (keep-alive) 還是單次的 (close)。
    • Cache-Control: 控制緩存行為。
    • Via: 顯示訊息經過的中間代理伺服器。
  2. 請求標頭 (Request Headers)：
    • 僅適用於 HTTP 請求。
    • Host: 請求的目標伺服器域名和埠號。這是 HTTP/1.1 中必須的標頭。
    • User-Agent: 發送請求的客戶端軟體資訊 (例如：瀏覽器類型和版本)。
    • Accept: 客戶端能夠接受的回應媒體類型 (MIME Type)。
    • Accept-Language: 客戶端偏好的語言。
    • Accept-Encoding: 客戶端支援的內容編碼方式 (例如：gzip, deflate)。
    • Cookie: 客戶端發送給伺服器的 Cookie 資訊。
    • Authorization: 包含客戶端的認證憑證 (例如：Basic 或 Bearer token)。
    • Referer: 導向當前請求的來源頁面 URL (拼寫錯誤的歷史遺留)。
  3. 回應標頭 (Response Headers)：
    • 僅適用於 HTTP 回應。
    • Server: 伺服器軟體的資訊。
    • Set-Cookie: 伺服器發送給客戶端的 Cookie 資訊，瀏覽器會儲存。
    • Content-Type: 回應 Body 中的數據類型 (MIME Type)。
    • Content-Length: 回應 Body 的位元組長度。
    • Last-Modified: 資源上次修改的時間。
    • Expires: 資源過期時間 (用於緩存)。
    • Location: 用於重定向 (3xx 狀態碼時，指示新的 URL)。
    • WWW-Authenticate: 伺服器要求客戶端進行認證 (401 狀態碼時)。
    • Strict-Transport-Security (HSTS): 強制客戶端使用 HTTPS 連線。
  4. 實體標頭 (Entity Headers)：
    • 適用於包含 Body 的請求和回應。
    • Content-Type: Body 中數據的媒體類型 (MIME Type)。
    • Content-Length: Body 的長度 (位元組)。
    • Content-Encoding: Body 的內容編碼方式 (例如：gzip，表示 Body 經過壓縮)。

Body (實體)

Body 部分是 HTTP 訊息中可選的部分，用於承載實際的數據內容。

定義格式：

  • Body 的格式完全取決於 Content-Type 標頭所指定的媒體類型。
  • 它可以是純文本、HTML、JSON、XML、圖片、影片、檔案等任何二進制或文本數據。
  • 如果請求或回應沒有 Body，則空行之後就沒有內容了。
  • Content-Length 標頭會指示 Body 的確切大小。如果 Content-Length 不存在，或者使用 Transfer-Encoding: chunked，則伺服器會通過關閉連線或特殊的塊結束標記來指示 Body 的結束。

功能：

Body 的主要功能是傳輸應用層的實際數據。

  • HTTP 請求中的 Body：
    • 主要用於 POST, PUT, PATCH 等請求方法，客戶端需要向伺服器提交數據。
    • 例如：在 POST 請求中，Body 可以包含提交的表單數據、JSON 格式的新用戶資訊、上傳的檔案內容等。
    • GET 請求通常不包含 Body，即使有，伺服器也應忽略。
  • HTTP 回應中的 Body：
    • 主要用於伺服器將請求的資源或處理結果返回給客戶端。
    • 例如：
      • GET 請求的回應 Body 可能包含 HTML 頁面、圖片檔案、JSON 格式的 API 數據。
      • POST 請求的回應 Body 可能包含新創建資源的 ID、處理成功的訊息或錯誤訊息。
      • PUT 請求的回應 Body 可能包含更新成功的確認訊息。

Header 和 Body 的關係

可以將 HTTP 訊息想像成一封信：

  • Header (標頭) 就像信封上的資訊：發件人、收件人、郵寄方式、信件類型 (掛號信/平信)、重量、郵編等。這些資訊幫助郵局和收件人知道如何處理這封信，但不是信件的實際內容。
  • Body (實體) 就像信封裡的信紙內容：這才是你真正想要傳達的訊息或數據。

兩者協同工作，確保 HTTP 請求和回應能夠被正確地發送、接收、解析和處理。

以寄送信件比喻 HTTP 請求與回覆的類型

  • GET (詢問信)： 想像你寫信問郵局：「請問 example.com/books/123 這個櫃位裡有什麼東西？」郵局會直接回覆你櫃位裡的內容。你的問題寫在信封（URL）上，不會另附一張紙（Request Body）。
  • POST (投遞信件)： 想像你寫一封信給郵局：「我這裡有一份新訂單，請幫我處理！」你把訂單內容寫在信紙上（Request Body），然後信封（URL）只寫郵局的地址。郵局處理完會回信給你說「訂單已處理，編號是 XYZ」。
  • PUT (更新/替換信件)： 想像你寫一封信給郵局：「請把 example.com/books/123 這個櫃位的舊內容，用我這封信裡寫的全新內容替換掉！」你把完整的新內容寫在信紙上（Request Body），信封（URL）上明確指定了要更新的櫃位。郵局會回信說「更新成功」。

1. MIME Type (Multipurpose Internet Mail Extensions) 媒體類型

MIME 類型最初是為電子郵件設計的，目的是讓電子郵件客戶端能夠識別附件的類型，以便正確地顯示或處理。後來，它被廣泛應用於 HTTP，作為識別 HTTP 請求或回應 Body 中數據內容類型的方式。

一個 MIME 類型通常由主類型 (major type) 和子類型 (subtype) 組成，中間用斜線 / 分隔，例如 text/html, image/jpeg, application/json。有時還會包含參數，例如 text/html; charset=utf-8。

MIME (用於表單數據) 的常見類型：

當透過 HTML 表單提交數據時，主要會使用兩種 MIME 類型：

  1. application/x-www-form-urlencoded
    • 用途： 這是 HTML 表單的預設內容類型，當您不特別指定 enctype 屬性時，表單數據會以這種格式提交。
    • 格式： 數據會被編碼成一系列的 鍵=值 對，這些對之間用 & 符號連接。所有的非英數字元（包括空格）都會被轉換為百分比編碼 (percent-encoding)，空格會被替換為 + 符號。
    • 範例： 如果表單有 <input name="name" value="John Doe"> 和 <input name="age" value="30"> 提交後的數據在 Request Body 中可能是：name=John+Doe&age=30
    • 特點：
      • 簡單、高效，適合傳輸簡單的鍵值對數據。
      • 所有數據都以字符串形式傳輸。
      • 不適合傳輸二進制文件 (例如圖片、文件)。
  2. multipart/form-data
    • 用途： 當表單中包含文件上傳 (file uploads) 字段時，必須使用這種內容類型。它允許將多種類型的數據（文本、二進制文件等）組合在一個請求中。
    • 格式： 請求的 Body 會被分成多個部分 (parts)，每個部分都代表表單中的一個字段或一個文件。每個部分都有其自己的 Content-Disposition 標頭 (指示字段名稱和文件名) 和 Content-Type 標頭 (指示該部分數據的實際類型)。這些部分之間用一個隨機生成的 boundary 字符串作為分隔符。

    • 範例 (簡化)：

      • 能夠混合傳輸多種類型的數據，包括文本和二進制文件。
      • 格式相對複雜，但能夠滿足文件上傳的需求。

JSON (JavaScript Object Notation) 格式

JSON 是一種輕量級的數據交換格式，易於人閱讀和寫入，也易於機器解析和生成。它基於 JavaScript 編程語言的一個子集，但已成為一種獨立於語言的數據格式，廣泛應用於 Web 服務 (API)、配置檔案、數據存儲等領域。

JSON 的基本結構：

JSON 數據主要由兩種結構構成：

  1. 物件 (Object)：
    • 由鍵值對 (key-value pairs) 的無序集合組成。
    • 鍵 (key) 必須是字符串，值 (value) 可以是字符串、數字、布林值、null、物件或陣列。
    • 用花括號 {} 包裹。
    • 範例：{ "name": "Alice", "age": 30 }
  2. 陣列 (Array)：
    • 由值的有序列表組成。
    • 值 (value) 可以是字符串、數字、布林值、null、物件或陣列。
    • 用方括號 [] 包裹。
    • 範例：[ "apple", "banana", "cherry" ] 或 [ { "id": 1 }, { "id": 2 } ]

JSON 的數據類型：

JSON 支持以下數據類型的值：

  • String (字符串)： 雙引號 " " 包裹的 Unicode 字符序列 (例如: "Hello World")。
  • Number (數字)： 整數或浮點數 (例如: 123, 3.14, -10)。
  • Boolean (布林值)： true 或 false。
  • Null (空值)： null。
  • Object (物件)： { key: value, ... }。
  • Array (陣列)： [ value, value, ... ]。

JSON 的 MIME Type：

  • 當發送或接收 JSON 數據時，HTTP Header 中的 Content-Type 通常會被設置為：
    • application/json

JSON 的功能和優勢：

  • 輕量級： 相較於 XML，JSON 的語法更簡潔，文件大小通常更小。
  • 易於閱讀和寫入： 其結構清晰，人眼容易理解。
  • 易於解析和生成： 大多數主流編程語言都內建或有成熟的函式庫來解析和生成 JSON 數據。
  • 跨平台/語言： 由於其簡單的文本格式，JSON 成為不同系統和編程語言之間交換數據的標準格式。
  • 應用場景：
    • RESTful API： 這是 Web API 最主要的數據交換格式。
    • Ajax 請求： 瀏覽器與伺服器之間進行非同步數據傳輸。
    • 配置檔案： 許多應用程式使用 JSON 作為其配置檔案格式。
    • 數據存儲： NoSQL 資料庫 (如 MongoDB) 常以 JSON 或類 JSON 格式存儲數據。
