Ollama vs. Hugging Face

  • Hugging Face
    • The Cloud Platform & Ecosystem
    • Central Hub / Repository
    • Cloud Inference APIs & Hosted Endpoints
    • Think of Hugging Face as the GitHub + AWS for AI:
      • Cloud Storage (Hub): It hosts millions of model files, datasets, and code repositories contributed by Google, Meta, Microsoft, and community researchers.
      • Cloud Services (Inference APIs): If you don't want to run a model on your local computer, Hugging Face lets you run models on *their* cloud GPUs via HTTP API requests (paying per token or per server hour).
  • Ollama
    • The Local Desktop Application
    • Think of Ollama as the local engine / local runner:
      • Desktop Application: It installs directly on a local PC/Mac and manages local GPU/CPU hardware.
      • Offline Execution: It downloads model files (which originated on Hugging Face) onto the computer's hard drive and runs them 100% offline.
      • Local API: It provides a local web server (http://localhost:11434) so local Python scripts or LangChain applications can talk to the model without touching the internet.
    • Pulls Model Files (.gguf) from HuggingFace
  • How They Work Hand-in-Hand in Development
  • When developers build AI applications, they often move between both platforms:
    1. Discovery (Hugging Face): A developer goes to Hugging Face to read model benchmarks, test a live web demo, and find a quantized version of a model (like gemma2:2b).
    2. Local Deployment (Ollama): The developer uses Ollama on their desktop to pull that model file down from the cloud and run it locally.
    3. App Integration (LangChain): The developer writes a Python program (like a RAG system) that sends requests to Ollama running locally on their PC.
    4. Cloud Scaling (Hugging Face - Optional): If the application grows and needs to be deployed to thousands of online web users, the developer might upload the fine-tuned model back to Hugging Face and host it using Hugging Face's Cloud Inference Endpoints.

Ollama vs Gemma

The Video Game Analogy
ComponentAnalogyReal World
GemmaThe Game Disc / ROM DataTrained Data (Weights)
It contains billions of numbers (mathematical parameters) learned during training. It is passive data and **cannot execute itself**.
OllamaThe Game ConsoleThe Software Program / Engine
It is the actual executable program (.exe) written in Go/C++. It loads Gemma's data into RAM/VRAM, does the math, and handles network APIs.

Ollama vs Gemma

  • What is Gemma ?
    • Gemma is essentially a large binary file (usually in .gguf format) containing matrices of floating-point numbers (called "weights" or "parameters").
    • A 2-billion parameter model (gemma2:2b) contains roughly 2 billion numbers that represent the model's "knowledge" and language patterns.
    • It has no code, no logic, and no running processes. It is pure static data.
  • What is Ollama ?
    • Ollama is an execution engine and web server. When you type ollama run gemma2:2b, Ollama performs the following steps:
      1. Loads the File: Reads the gemma2:2b weight file from your hard drive into your computer's RAM or GPU VRAM.
      2. Runs the Math: Uses C++ / CUDA code (via llama.cpp under the hood) to calculate matrix multiplications using those weights.
      3. Exposes the Interface: Provides a CLI (terminal interface) and a local REST API (http://localhost:11434) so external programs like LangChain or web browsers can talk to it.
  • The core "program logic" (algorithm) across almost all Large Language Models is virtually identical. What makes GPT-4, Llama 3, Gemma, and Mistral different from one another is almost 100% the trained parameters (weights) and datasets.
  • Gemma is the "brain/knowledge" (data), while Ollama is the "body/engine" (program) that makes the brain think and speak.

Connecting LangChain to Ollama + Gemma

pip install langchain-ollama langchain-core

# the Python Program
from langchain_ollama import OllamaLLM

# 1. Connect LangChain to your local Ollama instance running Gemma
# (Ollama defaults to http://localhost:11434)
llm = OllamaLLM(model="gemma2:2b")

# 2. Send a prompt to the local model
prompt = "Please explain what an LLM is in 2 simple sentences in Traditional Chinese."
response = llm.invoke(prompt)

print(response)

        • 什麼是 Python 的迴圈？請用簡單的比喻解釋。
        • 請幫我寫一封感謝老師指導的 E-mail 草稿。
    • 🚪 如何退出對話？
      • 在 >>> 後輸入 /bye 並按 Enter，即可退出聊天模式。
    • Hint: Windows: C:\Users\<使用者名稱>\.ollama\models
    • 可在終端機輸入 ollama list，如果能列出已安裝的模型列表，代表服務運作正常。

Ollama 大量安裝

  • 📦 Phase 1: Preparation on Teacher's PC (Do Once)
    1. Download the Ollama Installer:
      • Download OllamaSetup.exe (Windows) or Ollama-darwin.zip (Mac) from ollama.com.
    2. Download the Gemma Model:
      • Run the installer on the teacher's PC, then open Command Prompt / Terminal and run: ollama run gemma2:2b
      • Wait for the download to finish. Test a quick message to ensure it works, then exit with /bye.
    3. Copy the downloaded model files:
      • [Windows] C:\Users\\.ollama\models
  • 💻 Phase 2: Student PC Installation (Takes ~1 Minute per PC)
    1. Install Ollama
      • Double-click OllamaSetup.exe from the shared network drive to install the software.
    2. Copy the Model Folder
      • Copy the pre-downloaded .ollama folder from the network drive and paste it into their own User folder: C:\Users\Users\.ollama\
      • (Make sure the folder structure ends up as .../.ollama/models/manifests/... and .../.ollama/models/blobs/...)
  • Step 3: Run Without Internet!
    • Open Command Prompt / Terminal and type: ollama run gemma2:2b
    • Because the model files are already in the .ollama folder, Ollama will launch INSTANTLY without downloading anything from the internet.
    • You can tell Ollama to load models from a secondary drive (e.g., D:\OllamaModels) using an Environment Variable:
      1. Copy the models folder to D:\OllamaModels.
      2. Set the Environment Variable in Windows:
        • Key: OLLAMA_MODELS
        • Value: D:\OllamaModels
      3. Now Ollama will read models directly from drive D:\ every time without needing re-downloads!

RAG vs. LLM

RAG Embedding 空間 LLM Hidden States 向量空間
主要
功能		 檢索（Retrieval） 推理與生成（Reasoning & Generation）
幾何
特性		 依賴靜態語意相似度（距離近 = 意思像）。 依賴動態上下文與文法流向（座標會隨上文隨時跳轉）。
優化
目標		 把同義詞的距離拉近，異義詞推遠（Contrastive Loss）。 讓下一個正確 Token 的機率最大化（Cross-Entropy Loss）。
直觀
比喻		 靜態的百科全書分類索引（相同的放在一起）。 思考中的大腦神經元聯想網（從主詞推導到動詞，再推導到賓詞）。
「RAG 用的 Embedding 模型，像是在高維空間裡幫資料打卡劃分區域，目的是為了快速搜尋；而 LLM 模型學習後的權重與高維空間，像是在高維空間裡畫出出一條條流暢的思考路線圖。LLM 輸出向量的目的是為了指引下一個字該走向字典裡的哪一個 Token，因此它包含的不只是『意思相近』，更包含『邏輯與文法的必然性』。」

資料空間

  • LLM 內部（如 Transformer 隱藏層）與輸出層的確都在高維度空間中運作，但它們的高維空間「幾何特性」與純 Embedding 模型截然不同：它不僅僅代表「靜態語意相近」，更包含了「動態語意轉譯」、「上下文邏輯推理」與「語法流暢度（下一個字出現的機率）」。
  • 靜態語意空間 vs. 動態上下文空間
    • 純 Embedding 模型（靜態語意空間）：
      • 無上下文（或僅有局部上下文）的靜態語意距離。
      • 在這個空間裡，蘋果（水果）和 香蕉 的距離永遠很近；蘋果 和 台積電 距離很遠。
    • LLM 隱藏層（動態上下文空間）：
      • LLM 每經過一層 Transformer 區塊（Self-Attention），這個 Token 在高維空間的座標就會被重新修正與轉移。
      • 例如： 輸入「蘋果發表了全新的 M4 晶片」，經過 Self-Attention 後，蘋果 這個 Token 的向量座標會被拉離「水果空間」，瞬間移動到「科技/半導體/上市公司」的高維空間，並且與 台積電、晶圓代工 的距離大幅縮短。
      • 結論： LLM 的高維空間不是不具備語意相近性，而是它的語意是動態且高度依賴上下文（Context-aware）的。
  • LLM 的輸出層（Unembedding / LM Head）：從高維座標轉為機率
    • 當資料經過 LLM 所有隱藏層後，最後會來到輸出層（LM Head）。
    • 最後的高維向量：
      • 模型的最後一層會產出一個代表「目前為止所有上下文總結」的高維向量（例如 4096 維）。
    • 與字典求內積（Dot Product）：
      • 輸出層有一個巨大的矩陣（稱為 Unembedding Matrix），裡面記錄了字典裡每一個 Token（例如 32,000 個 Token）的高維特徵向量。
    • 計算夾角與相似度：
      • 系統計算最後高維向量與字典中每個 Token 向量的相似度（Logits）。
    • Softmax 轉換：
      • 把這些相似度數值轉化為 0~1 之間的「下一個字出現機率」。
  • 為什麼「語意不相近」的字機率可能更高？
    • 因為 LLM 學習權重的目標是「預測合理的下一個 Token（Next Token Prediction）」，這包含了語法規則與對話邏輯
  • 例如：「這家銀行的放款審查非常_____」
    • 在高維空間中，嚴格（形容詞）和 放款（動詞/名詞）在靜態語意上完全不相近。
    • 但因為文法結構（主詞+副詞+形容詞）以及金融語意邏輯，LLM 內部高維向量在最後預測時，會將幾何位置推向「描述審查品質的形容詞」區域，使得 嚴格 或 謹慎 的出現機率最高，而不是語意最相關但文法不對的 貸款。

建立地端知識庫（離線/初始化作業）

  • 1. 文件讀取與文本切分（Document Loading & Chunking）
    • 目的： 消除 LLM 上下文長度限制，並提升搜尋精準度。
    • 做法： 使用 PyPDFLoader 讀取金融文件/條款，並用 RecursiveCharacterTextSplitter 切分成小塊（Chunks）。
    • 實作關鍵設定：
      • chunk_size（塊大小）：建議設為 500 ~ 800 字（避免把財務表格切斷）。
      • chunk_overlap（重疊字數）：建議設為 100 字（保證上下文語意連貫不中斷）。
      • 保留 Metadata： 必須保留頁碼（page）、檔名等資訊，作為後續 RAG 引文註腳的依據。
  • 2. 向量化與向量資料庫儲存（Embedding & Vector Store）
    • 目的： 將切分好的文字區塊轉換為「高維語意座標」，並建立快速索引。
    • 做法： 使用地端 Embedding 模型（如 BAAI/bge-small-zh-v1.5），將每一個 Chunk 轉為向量後存入地端向量資料庫（如 ChromaDB 或 FAISS）。
    • 優點： 完全在地端 CPU/GPU 運作，敏感的金融文件不會外流到公有雲。

檢索與生成（線上/即時對話）

  • 3. 語意檢索（Similarity Search）
    • 目的： 從資料庫中快速精準地撈出與問題最相關的資料。
    • 做法： 當審查員輸入問題（例如：「本案的負債比率是多少？」）時：
      • 將問題同樣經過 Embedding 模型轉換為向量。
      • 向量資料庫計算餘弦相似度（Cosine Similarity），撈出前 K 個最相關的文本區塊。
  • 4. 組合提示詞（Prompt Assembly）
    • 目的： 設定模型的角色，並將「撈出來的參考資料」與「使用者問題」拼裝在一起。
    • Prompt 結構範例：
      你是一位嚴謹的金融授信審查員。請「嚴格根據」以下參考資料回答問題。
如果資料中沒有提及，請直接回答「文件中未提供」，切勿憑空捏造。
回答時必須在句末標註引用頁碼，格式為：(參照第 X 頁)。

【參考資料】：
[片段 1 - 第 12 頁]: 本年度公司負債總額為 1.2 億元...
[片段 2 - 第 25 頁]: 流動負債包含短期借款...

【提問】：本案的負債比率與流動負債狀況為何？
  • 5. 地端 LLM 生成回答（Inference with Ollama Gemma）
    • 目的： 讓 LLM 看著資料寫出結構化、閱讀體驗良好的分析回答。
    • 做法： 將組裝好的 Prompt 送入地端 Ollama 的 Gemma 2 (2B 或 9B)。
    • 參數設定建議：
      • temperature 設為 0.1（極低溫，防止模型自由發揮，降低幻覺）。
      • top_p 設為 0.9。
